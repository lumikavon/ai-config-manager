# Core design and storage contract

The Rust core is the only authority for reading credentials. The frontend receives only a masked presence flag. `None` in a save request preserves the saved credential; an empty supplied credential is invalid. Revisions hash exact bytes, while history hashes normalized complete YAML semantics after decryption. Mapping keys are sorted and encryption nonces are excluded from semantic hashes. Explicit nulls and numeric/string types remain distinct. Only a single YAML document, string mapping keys, and untagged values are accepted. Duplicate keys and malformed input are rejected without echoing parser excerpts.

The process takes an OS advisory exclusive lock before reading or writing, checks an exact-byte revision, and atomically replaces a same-directory staged file. All cooperating clients use the same lock. A noncooperating external writer is checked again immediately before replacement, but cannot be made transactionally cooperative by a filesystem API. Symlinks are rejected at file and ancestor boundaries. Files are restricted to the current account (0600 on Unix; protected current-user DACL on Windows). Parent directory symlink races by a malicious actor with write access remain outside the trust boundary; use a private home/config directory.

History contains only redacted field changes and backend-generated semantic SHA-256 values, never a plaintext or encrypted key. A durable pending journal contains the intended revision and next redacted history. Recovery commits history only if the current configuration matches the intended revision, or discards an uncommitted journal when the prior revision still matches. Divergent state blocks saves for manual recovery. Reads of configuration are independent of history health. The ten newest entries are retained. Staged secret files are removed on errors, and any abandoned secret stage is mode 0600.

AES-256-GCM encrypts with a random 96-bit nonce and authenticated versioned associated data. The envelope is `ENC(v1:BASE64(nonce || ciphertext || tag))`. The 256-bit key lives in the native OS credential vault, not in configuration or history. Tests inject an in-memory vault and never access user configuration or the system vault.

## Public API and error handling

`Store::new(PathBuf, Arc<dyn Vault>)` resolves relative paths against the current directory. `load()` returns `ConfigView`; `save(SaveRequest)` uses the desktop source; `save_with_source(request, source)` accepts `desktop`, `cli`, `skill`, or `test`. `history()` returns newest-first redacted entries. `with_config` calls an in-process closure with a consistent `ConfigSnapshot` containing base URL/model and a `with_secret` accessor. `with_secret` and `validate_secret` are convenience operations; neither serializes the credential. `Vault::get_key` never creates missing keys; `create_key` is only used for encryption. `NativeVault` serializes first creation across configuration paths using a private global lock, then rereads the vault under that lock.

Locks time out after five seconds (`LOCK_TIMEOUT`). No lock bypass or force overwrite exists. The caller must reload on `CONFLICT`. A `HISTORY_PENDING` response means configuration replacement succeeded but history finalization remains pending; reload configuration and retry reading history, never assume the save failed. `HISTORY_CORRUPT` blocks writes but not ordinary configuration reads. `KEY_MISSING`, `VAULT_UNAVAILABLE`, and `DECRYPT_FAILED` are distinct. Other codes include `INVALID_CONFIG`, `INVALID_URL`, `INVALID_MODEL`, `INVALID_KEY`, `INVALID_SOURCE`, `UNSAFE_PATH`, `TOO_LARGE`, `ENCRYPT_FAILED`, and `IO`. Error messages are fixed strings and never include parser excerpts, raw input, key material, or OS errors.

The file-size limit is 2 MiB and the accepted value depth is 64. The parser additionally enforces its own recursion and alias-repetition limits. URL length is capped at 8192 bytes, model at 1024, and API key at 65536. Existing overlong field values are summarized, not copied into history; generated history is validated before the configuration commit. YAML comments, styles, and anchor syntax are not preserved, but unrelated accepted values are. Semantic hashes are sensitive equality fingerprints of the complete plaintext configuration, not authentication or signatures; do not publish them. They are stable across map order, encryption toggles, and random nonces, not across substantive scalar-type changes.

All configuration-path ancestors must be actual directories, not symlinks. In particular, on macOS a caller choosing a temporary directory through `/var` should resolve the legitimate directory first (for example, to `/private/var`). The default user-home configuration path normally needs no such adjustment. Windows code is cross-compiled in verification, but native vault/UI/ACL behavior still requires runtime smoke testing on supported Windows/macOS hosts.

Every save writes a fresh random transaction ID as a nonsecret YAML comment and uses the same ID for its history entry. Thus even byte-equivalent plaintext values have distinct raw revisions, while the semantic hash stays unchanged. A journal records the exact prior history-byte hash from the same read that parsed the history. Recovery only installs intended history when the configuration matches the intended transaction and current history still matches that prior hash; already-installed intended history is idempotent. A stale or divergent history/journal pair blocks rather than rolling newer entries back. Pre-replacement and post-replacement failures are covered by synthetic fault injection. If replacement succeeded but a later durability step failed, the result is `HISTORY_PENDING`; if the resulting configuration cannot be identified, the result is `COMMIT_UNCERTAIN`. The latter requires reloading/checking before retrying, not assuming no change occurred.

## Native vault identity and durability boundary

The keyring service name is `ai-config-manager`; the account/user label is `config-encryption-v1`. The stored binary secret is exactly 32 bytes. All configuration paths used by this OS account intentionally share that entry; first creation is serialized using `~/.config/.ai-config-manager-vault.lock`. Windows builds select keyring `windows-native`, macOS selects `apple-native`, Linux selects `sync-secret-service` plus `crypto-rust` and `vendored`. No production feature selects the mock provider. Unsupported platforms are not advertised as supported.

A read of existing ENC calls only `get_key`. Missing entries are not recreated. An explicit new API Key can be saved by the user to replace unrecoverable ciphertext, creating a new vault key if no entry remains; this does not recover other files encrypted with the lost key. Back up configuration and the native credential store together. There is no plaintext data-key backup or machine-portable export.

Durability relies on the OS/filesystem honoring file synchronization, same-directory replacement, and directory synchronization where available. Windows uses file flush plus MoveFileExW(REPLACE_EXISTING | WRITE_THROUGH); it does not claim an independently journaled kernel transaction or guarantee against faulty storage hardware. A power loss can still require recovery from backups. The recovery sidecar detects supported interrupted commits; it is not a substitute for backups or an authenticated audit ledger.
